# fix460 — Inline List Content history and master-content permissions

List Content previously opened at the end of the entire table, and its independent save path kept only the latest text. It now opens in the corresponding employee cell under the selected HOOK. The expanded cell shows current text and recorded prior versions. The receive-work form and inline editor share the same ETag-checked online save function. A changed save includes the preceding server-confirmed text and timestamp in the same conditional write; identical retries do not add a revision.

Refreshing content retains the active editor node, draft and focus. Switching table filters retains an open editor above the table if its original cell is hidden. Account changes remove the previous account's editor. Closing a dirty editor asks before discarding; leaving the page while dirty or saving triggers the browser's unsaved-change protection. Failed/offline/concurrent saves retain text and do not claim online success. A read-only open history refreshes with the latest accessible server data.

Only authenticated Supervisor (`sup`), Specialist (`spec`) and Audit (`audit`) see the master management column or invoke master add/edit/delete, bulk/import or persistence entry points. Firebase rules also restrict `content_tracker_v2` writes to active users in those roles. Employees retain their own List Content writes. Existing Supervisor/Audit cross-employee text read permissions and Supervisor-only product catalog management are unchanged. Delayed delete confirmation rechecks the current role.

Validation: 117/117 regression scripts; seven isolated browser suites (full functional navigation, Audit persistence, review rounds, cross-device sync, auth recovery, conflict recovery, and new inline content flow). New browser coverage exercises two HOOKs from the receive-work component, another role's browser reading the result, inline save/history, offline retry, direct employee management denial and fresh-page persistence. Unit coverage additionally checks simultaneous edits, draft/focus retention, role changes and HOOK separation. Firebase Database Emulator verifies master roles, owner-only texts, prior-snapshot validation, historical text modification denial, and rejection of old current-only writes that would erase history. Existing quota and partial-success tests remain passing. HTML: 637,248 bytes.

Release scope: History predating this release cannot be reconstructed when it was never stored. On the next edit, the preceding online text becomes the first known historical snapshot. Existing older clients need the current release to save this schema; the shared release updater remains enabled. No real employee work or Audit decision was changed to run tests. Production rules, public asset hashes and signed-in UI are verified as part of deployment; isolated browser tests do not establish that every physical employee device is currently connected.
