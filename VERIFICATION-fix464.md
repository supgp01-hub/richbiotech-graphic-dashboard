# fix464 — Audit deduction increases and removals

Audit item details now show the original amount, manual additions and effective total. Supervisor and Audit can add a positive whole-baht amount with a reason, or remove the logical charge from the calculation with a reason. Removed charges are available under the removed-items status filter. The change retains the existing confirmation/pending status semantics; daily revision charges still share one employee/day total, with a scope notice in the dialog.

Changes are separate immutable events in `audit_deduction_adjustments_v1`, so source-sheet refreshes and the existing deduction store cannot overwrite the adjustment history. Removal takes precedence over all additions. Each operation uses one stable id and a conditional create; a retry after a lost acknowledgement verifies that operation rather than charging again. A stale amount from another device requires a review of the refreshed preview. Forms remain open on failure and normal navigation is guarded while the result is uncertain. Successful UI updates require a read-back acknowledgement. Confirmed records are cached per signed-in account; unavailable online verification is visibly flagged.

Database rules allow only active Supervisor/Audit accounts to append adjustment events. They reject replacement/deletion of history, collection overwrites, invalid amounts, spoofed authors, and non-server timestamps. Existing database paths and permissions are unchanged. Existing active-account read access matches the audit data model; the employee UI remains scoped to their own items and has no amount-management controls.

Validation: 119 regression scripts, ten isolated browser suites including actual audit UI add/remove, two independent browser contexts, offline draft retention, concurrent preview review, acknowledgement loss/retry, history, source reload and employee controls. Local database emulator tests cover the new rules and the existing content-submission permissions. The initial HTML remains below 640,000 bytes.

Deployment verification includes rules read-back, GitHub regression/Pages success, public file hashes, and the signed-in production UI. No production employee deduction was created, increased or removed for testing. Browser tests use isolated fixtures; physical employee devices were not individually tested. Offline edits remain in the open form and require retry when connectivity returns; an explicitly forced browser shutdown can discard an unsubmitted form.
